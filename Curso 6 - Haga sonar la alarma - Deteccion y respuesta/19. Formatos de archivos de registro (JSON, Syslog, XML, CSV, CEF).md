# Formatos de Archivos de Registro en Ciberseguridad: JSON, Syslog, XML, CSV y CEF

En esta guía del **Curso 6: Haga sonar la alarma: Detección y respuesta**, se exploran en detalle los principales **formatos de archivos de registro (*log file formats*)** utilizados en la industria de la ciberseguridad. Como analista en un **SOC (Centro de Operaciones de Seguridad)**, la habilidad para inspeccionar, decodificar e interpretar registros provenientes de fuentes heterogéneas es indispensable para reconstruir incidentes. Se analizan la sintaxis, componentes, ventajas, desventajas y casos de uso de **JSON**, **Syslog**, **XML**, **CSV** y **CEF (Common Event Format)**.

---

## 1. El Desafío de la Heterogeneidad de Registros en el SOC

En una infraestructura corporativa conviven servidores Linux, controladores de dominio Windows, cortafuegos perimetrales, servicios en la nube (AWS/GCP/Azure) y aplicaciones web personalizadas. Cada uno de estos entornos genera telemetría en formatos radicalmente distintos.

```
┌──────────────────────────────────────────────────────────────────────────────┐
│                    EL PAPEL DEL SIEM EN LA NORMALIZACIÓN                     │
├──────────────────────────────────────────────────────────────────────────────┤
│ Las herramientas SIEM (Splunk, Chronicle, Sentinel) reciben logs en múltiples│
│ formatos crudos y utilizan parsers (analizadores sintácticos) para extraer   │
│ campos clave (IP origen, IP destino, usuario, hash) en un esquema común.    │
│ Comprender los formatos subyacentes permite al analista auditar las reglas de│
│ detección y escribir consultas de búsqueda avanzadas sin depender de la GUI. │
└──────────────────────────────────────────────────────────────────────────────┘
```

## 2. Formato JSON (JavaScript Object Notation)

**JSON** es un formato de texto ligero, abierto y universalmente adoptado para el intercambio de datos estructurados. Es el estándar de facto en **entornos de nube**, interfaces de programación de aplicaciones (**REST APIs**), entornos de contenedores (**Kubernetes/Docker**) y soluciones modernas de seguridad.

### Componentes Sintácticos de JSON
* **Pares Clave-Valor:** Una clave entre comillas dobles seguida de dos puntos y su valor correspondiente: `"severity": "HIGH"`.
* **Comillas Dobles:** Obligatorias para cadenas de texto (*strings*). Los valores numéricos (`1090`) y booleanos (`true`/`false`) no llevan comillas.
* **Comas:** Separan pares clave-valor dentro de una misma estructura.
* **Llaves `{ }`:** Delimitan un **Objeto**, que puede contener múltiples atributos o incluso otros objetos anidados.
* **Corchetes `[ ]`:** Delimitan un **Array** (lista ordenada de valores).

### Ejemplo de Registro de Seguridad en JSON

```json
{
  "timestamp": "2026-09-19T18:15:30.104Z",
  "event_type": "AUTHENTICATION_FAILURE",
  "source": {
    "ip": "198.51.100.45",
    "port": 54210,
    "geo_country": "RU"
  },
  "target": {
    "host": "srv-finance-01.corp",
    "service": "SSH"
  },
  "user": {
    "username": "root",
    "exists": true,
    "privilege_level": "ADMINISTRATOR"
  },
  "attempt_count": 14,
  "blocked_by_fail2ban": true
}
```

```
┌──────────────────────────────────────────────────────────────────────────────┐
│ VENTAJAS DE JSON                     │ DESVENTAJAS DE JSON                   │
├──────────────────────────────────────┼───────────────────────────────────────┤
│ • Altamente estructurado y jerárquico│ • Mayor sobrecarga de caracteres      │
│ • Nativo en entornos Cloud y APIs.   │   (llaves, comillas) que CSV.         │
│ • Fácil de parsear automáticamente.  │ • Puede ser verboso si no se comprime.│
└──────────────────────────────────────┴───────────────────────────────────────┘
```

## 3. Formato Syslog (RFC 5424 y RFC 3164)

**Syslog** es el estándar histórico de registro nativo en sistemas operativos **Unix/Linux** y dispositivos de red (routers Cisco, switches, firewalls).

El término Syslog abarca tres dimensiones distintas:
1. **Protocolo:** Transporte de mensajes a través de la red usando el puerto **UDP/TCP 514** (texto plano) o **TCP 6514** (Syslog seguro sobre TLS).
2. **Servicio / Demonio:** Software local (`rsyslog`, `syslog-ng`) que recopila, filtra y reenvía los eventos.
3. **Formato:** La estructura interna del mensaje según los estándares **RFC 3164** (BSD tradicional) o **RFC 5424** (Syslog moderno).

### Componentes de una Entrada Syslog RFC 5424

```
┌──────────────────────────────────────────────────────────────────────────────────────────┐
│                             ESTRUCTURA DE UN REGISTRO SYSLOG                             │
├─────────┬───────────────────────────────────┬────────────────────────────┬───────────────┤
│ <PRI>   │ CABECERA (HEADER)                 │ DATOS ESTRUCTURADOS (SD)   │ MENSAJE (MSG) │
├─────────┼───────────────────────────────────┼────────────────────────────┼───────────────┤
│ <236>1  │ 2026-03-21T01:11:11.003Z host app │ [user@32473 eventID="999"] │ Payload libre │
└─────────┴───────────────────────────────────┴────────────────────────────┴───────────────┘
```

#### 1. El Campo de Prioridad (`<PRI>`)
Indica la urgencia del evento. El valor numérico se calcula combinando la instalación de origen (*Facility*) y el nivel de gravedad (*Severity*):
$$\text{PRI} = (\text{Facility} \times 8) + \text{Severity}$$

* **Niveles de Gravedad (0 a 7):**
  * `0`: Emergencia (*Emergency - Sistema inutilizable*).
  * `1`: Alerta (*Alert - Acción inmediata requerida*).
  * `2`: Crítico (*Critical*).
  * `3`: Error (*Error*).
  * `4`: Advertencia (*Warning*).
  * `5`: Notificación (*Notice*).
  * `6`: Informativo (*Informational*).
  * `7`: Depuración (*Debug*).
* **Regla:** Cuanto **más bajo es el número de severidad, más crítico** es el evento.

#### 2. Cabecera (Header)
Contiene la versión de protocolo, la marca temporal en formato ISO 8601 con zona horaria UTC (`Z`), el nombre de host emisor (`virtual.machine.com`), el nombre de la aplicación (`evntslog`) y el identificador de proceso o mensaje (`ID01`).

#### 3. Datos Estructurados (*Structured Data*)
Conjuntos de pares clave-valor encerrados entre corchetes `[ ]` que proporcionan contexto sin ambigüedad:
`[user@32473 iut="1" eventSource="Application" eventID="9999"]`

#### 4. Mensaje (*Message*)
El texto descriptivo libre generado por la aplicación: `This is a log entry!`.

## 4. Formato XML (eXtensible Markup Language)

**XML** es un lenguaje de marcado basado en etiquetas jerárquicas utilizado ampliamente para almacenar e intercambiar datos estructurados. Es el formato nativo subyacente de los **Registros de Eventos de Microsoft Windows (*Windows Event Logs - .evtx*)**.

### Componentes de XML
* **Etiquetas (*Tags*):** Encierran los datos entre paréntesis angulares. Toda etiqueta de apertura `<Event>` debe tener su etiqueta de cierre correspondiente `</Event>`.
* **Elementos (*Elements*):** Incluyen la etiqueta y el contenido interior. Existe siempre un **elemento raíz (*root*)** que contiene a los **elementos hijos (*child elements*)**.
* **Atributos (*Attributes*):** Pares clave-valor ubicados dentro de la etiqueta de apertura para aportar metadatos, delimitados por comillas simples o dobles: `<Data Name='SubjectUserName'>JSMITH</Data>`.

### Ejemplo Real: Event ID 4688 de Windows (Creación de Procesos)

```xml
<Event xmlns='http://schemas.microsoft.com/win/2004/08/events/event'>
  <System>
    <Provider Name='Microsoft-Windows-Security-Auditing' Guid='{54849625-5478-4994-a5ba-3e3b0328c30d}'/>
    <EventID>4688</EventID>
    <Version>2</Version>
    <Level>0</Level>
    <TimeCreated SystemTime='2026-09-19T16:42:00.128450Z'/>
    <Computer>DC-PRIMARY.corp.local</Computer>
  </System>
  <EventData>
    <Data Name='SubjectUserName'>ADMIN_TI</Data>
    <Data Name='SubjectDomainName'>CORP</Data>
    <Data Name='NewProcessId'>0x1404</Data>
    <Data Name='NewProcessName'>C:\Windows\System32\WindowsPowerShell\v1.0\powershell.exe</Data>
    <Data Name='CommandLine'>powershell.exe -enc SQBFAFgA...</Data>
  </EventData>
</Event>
```

```
┌──────────────────────────────────────────────────────────────────────────────┐
│ VENTAJAS DE XML                      │ DESVENTAJAS DE XML                    │
├──────────────────────────────────────┼───────────────────────────────────────┤
│ • Muy riguroso y validable por XSD.  │ • Sintaxis extremadamente pesada y    │
│ • Estándar universal en ecosistemas  │   verbosa (alto consumo de bytes).    │
│   Windows Enterprise (AD / GPO).     │ • Parsing computacionalmente costoso. │
└──────────────────────────────────────┴───────────────────────────────────────┘
```

## 5. Formato CSV (Comma Separated Values)

**CSV** es un formato plano donde cada línea representa una fila de una tabla y los valores de cada columna están separados por **comas** (o caracteres delimitadores como punto y coma `;` o tabulaciones `\t` en TSV).

### Estructura Posicional y Ausencia de Esquema en Línea
A diferencia de JSON o XML, los registros CSV individuales **no incluyen los nombres de los campos**; la interpretación del dato depende estrictamente de su **posición en la fila**:

```text
# Formato de Encabezado:
# timestamp,action,src_ip,src_port,dst_ip,dst_port,protocol,verdict,sig_id,alert_name,severity

2026-11-24T21:27:09.534255,ALERT,192.168.2.7,1041,198.51.100.50,80,TCP,ALLOWED,1:2001999:9,"ET MALWARE Spyware Downloading Ads",1
```

* **Posición 1:** Marca temporal (`2026-11-24T21:27:09.534255`).
* **Posición 3 y 4:** IP origen (`192.168.2.7`) y Puerto origen (`1041`).
* **Posición 5 y 6:** IP destino (`198.51.100.50`) y Puerto destino (`80`).
* **Posición 10:** Nombre de la firma de detección (entre comillas dobles para evitar que la coma interna rompa el delimitador).

> [!WARNING]
> **Riesgo Operativo en CSV:** Si el dispositivo de origen (como un firewall o un NIDS Snort) actualiza su firmware y añade un nuevo campo en medio de la fila sin previo aviso, los parsers automáticos del SIEM desplazarán todos los valores, corrompiendo las consultas y las alertas.

## 6. Formato CEF (Common Event Format)

Creado originalmente por la empresa **ArcSight** (ahora OpenText), **CEF** es un estándar abierto diseñado específicamente para **facilitar la interoperabilidad entre dispositivos de seguridad y sistemas SIEM**.

Un registro CEF consta de **7 campos estándar prefijados** separados obligatoriamente por el carácter de tubería (`|`), seguidos por una sección opcional de **Extensiones** escritas en pares clave-valor:

```
┌──────────────────────────────────────────────────────────────────────────────┐
│                    SINTAXIS MAESTRA DEL FORMATO CEF                          │
├──────────────────────────────────────────────────────────────────────────────┤
│ CEF:Version|Device Vendor|Device Product|Device Version|Signature ID|Name|   │
│ Severity|Extension                                                           │
└──────────────────────────────────────────────────────────────────────────────┘
```

### Ejemplo de Registro CEF (Transportado sobre Syslog)

```text
Sep 19 08:26:10 firewall-edge CEF:1|SecurityVendor|ThreatManager|2.4|100|Worm Propagation Blocked|10|src=10.0.0.2 dst=198.51.100.2 spt=1232 dpt=445 cs1Label=MalwareFamily cs1=WannaCry
```

### Desglose Campo por Campo

```
┌───────────────────────┬──────────────────────────────────────────────────────┐
│ Campo CEF             │ Valor Extraído y Significado                         │
├───────────────────────┼──────────────────────────────────────────────────────┤
│ **Prefijo Syslog**    │ `Sep 19 08:26:10 firewall-edge` (Fecha y Host).      │
├───────────────────────┼──────────────────────────────────────────────────────┤
│ **Versión CEF**       │ `1` (Versión estándar de la especificación CEF).     │
├───────────────────────┼──────────────────────────────────────────────────────┤
│ **Device Vendor**     │ `SecurityVendor` (Fabricante del dispositivo).       │
├───────────────────────┼──────────────────────────────────────────────────────┤
│ **Device Product**    │ `ThreatManager` (Nombre de la solución de seguridad).│
├───────────────────────┼──────────────────────────────────────────────────────┤
│ **Device Version**    │ `2.4` (Versión del firmware o software).             │
├───────────────────────┼──────────────────────────────────────────────────────┤
│ **Signature ID**      │ `100` (Identificador único de la regla disparada).   │
├───────────────────────┼──────────────────────────────────────────────────────┤
│ **Name**              │ `Worm Propagation Blocked` (Descripción del evento). │
├───────────────────────┼──────────────────────────────────────────────────────┤
│ **Severity**          │ `10` (Escala del 0 al 10; 10 = Máxima criticidad).   │
├───────────────────────┼──────────────────────────────────────────────────────┤
│ **Extension**         │ `src=10.0.0.2 dst=198.51.100.2 spt=1232 dpt=445 ...` │
│                       │ Pares clave-valor con IPs, puertos y familia malware.│
└───────────────────────┴──────────────────────────────────────────────────────┘
```

## 7. Matriz Comparativa de Formatos de Registro

| Característica | **JSON** | **Syslog (RFC 5424)** | **XML** | **CSV** | **CEF** |
| :--- | :--- | :--- | :--- | :--- | :--- |
| **Entorno Predominante** | Cloud, Web, APIs, Microservicios | Linux, Unix, Switches, Routers | Windows Event Logs, Active Directory | Exportaciones de bases de datos, NIDS | Firewalls, WAFs, Antivirus hacia SIEM |
| **Estructura** | Jerárquica (Objetos/Arrays) | Encabezado + Pares KV + Texto | Jerárquica (Etiquetas/Atributos) | Tabular Posicional | Híbrida (Campos fijos + Pares KV) |
| **Facilidad de Lectura Humana** | Alta | Media-Alta | Media (Verbosa) | Baja (Sin cabecera) | Alta |
| **Eficiencia de Almacenamiento**| Media | Alta | Baja (Muy pesado) | Máxima (Ultra compacto) | Alta |
| **Riesgo de Rotura por Cambio** | Muy Bajo (Claves explícitas) | Bajo | Muy Bajo | Muy Alto (Cambio de orden) | Bajo |
| **Estandarización en SIEM** | Nativa | Nativa | Nativa vía WEF | Requiere mapeo manual | Diseñado específicamente para SIEM |

## 8. Consideraciones de Normalización: CIM y ECS

Cuando un analista escribe una regla en el SIEM para detectar un ataque de fuerza bruta, no puede escribir cinco reglas diferentes para cada formato de log. 

Para resolver esto, las plataformas implementan modelos de datos comunes:
* **Splunk CIM (*Common Information Model*):** Mapea campos como `src_ip` o `user` sin importar si provienen de un JSON de AWS o de un CEF de Fortinet.
* **Elastic ECS (*Elastic Common Schema*):** Estandariza campos bajo la nomenclatura `source.ip`, `destination.port`, `user.name`.

---

## 9. Puntos Clave para el Analista de Ciberseguridad

* **No existe un formato único:** El analista del SOC debe saber desenvolverse con soltura entre JSON, Syslog, XML, CSV y CEF.
* **Syslog es Triple:** Diferencia siempre el **protocolo** (UDP/TCP 514 / TLS 6514), el **servicio** (`rsyslog`) y el **formato** del mensaje.
* **Cuidado con CSV:** Nunca asumas el significado de una columna en un log CSV sin consultar la documentación oficial del fabricante del sensor.
* **Estructura CEF:** Recuerda los 7 campos delimitados por tubería (`|`) y que los datos detallados se ubican en la sección de *Extensiones* mediante pares clave-valor.
* **Precisión en Timestamps:** El estándar **RFC 3339 / ISO 8601** (ej. `2026-09-19T18:11:11.003Z`) es el estándar de oro para evitar errores por husos horarios.
