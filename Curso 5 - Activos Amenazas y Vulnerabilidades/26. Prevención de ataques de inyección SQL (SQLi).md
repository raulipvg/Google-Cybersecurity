# Prevención de Ataques de Inyección SQL (SQLi): Mecanismos, Tipologías y Estrategias Defensivas de Código Seguro

En esta guía exhaustiva del **Curso 5: Activos, Amenazas y Vulnerabilidades**, se analiza en profundidad la naturaleza de las **Inyecciones SQL** (*SQL Injection - SQLi*), su prevalencia en el **OWASP Top 10 (A03: Injection)**, el desglose de sus **tres categorías principales** (**En Banda**, **Inferencial / Ciega** y **Fuera de Banda**), la anatomía paso a paso de un ataque de evasión de autenticación, y las técnicas de remediación y blindaje en el código: **Consultas Parametrizadas (*Prepared Statements*)**, **Validación y Saneamiento de Entradas**, y el **Principio de Privilegio Mínimo en Bases de Datos**.

---

## 1. ¿Qué es una Inyección SQL (*SQLi*)?

El **Lenguaje de Consulta Estructurado (SQL)** es el estándar universal para almacenar, manipular y consultar información en **Sistemas de Gestión de Bases de Datos Relacionales (RDBMS)** como MySQL, PostgreSQL, Microsoft SQL Server, Oracle y SQLite.

Una **Inyección SQL (SQLi)** es una vulnerabilidad crítica de seguridad web que ocurre cuando datos no confiables introducidos por un usuario (mediante formularios de inicio de sesión, barras de búsqueda, parámetros de URL o cabeceras HTTP) se **concatenan directamente** dentro de una consulta SQL sin ser debidamente validados, filtrados o parametrizados. Esto permite al atacante engañar al intérprete de la base de datos para que ejecute comandos arbitrarios no previstos.

```
┌──────────────────────────────────────────────────────────────────────────────┐
│                    IMPACTO DE UN ATAQUE DE INYECCIÓN SQL                     │
├──────────────────────────────────────────────────────────────────────────────┤
│ • Pérdida de Confidencialidad: Extracción masiva de contraseñas, PII y pagos.│
│ • Pérdida de Integridad: Modificación de saldos bancarios, alteración de datos│
│ • Pérdida de Disponibilidad: Borrado total de tablas o bases de datos (DROP).│
│ • Control del Sistema: Ejecución de comandos en el SO (RCE mediante xp_cmdshell)│
└──────────────────────────────────────────────────────────────────────────────┘
```

## 2. Las Tres Categorías Principales de Inyección SQL

Los ataques de inyección SQL se clasifican según el **canal de comunicación** utilizado para lanzar el ataque y la forma en que el atacante **obtiene o infiere los datos**:

```
┌────────────────────────────────────────────────────────┐
│             CATEGORÍAS DE INYECCIÓN SQL (SQLi)         │
└──────────────────────────┬─────────────────────────────┘
                           │
 ┌─────────────────────────┼─────────────────────────┐
 ▼                         ▼                         ▼
┌───────────────────────┐ ┌───────────────────────┐ ┌───────────────────────┐
│       EN BANDA        │ │      INFERENCIAL      │ │    FUERA DE BANDA     │
│   (In-Band / Classic) │ │   (Inferential / Blind│ │     (Out-of-Band)     │
├───────────────────────┤ ├───────────────────────┤ ├───────────────────────┤
│ El ataque y la salida │ El atacante no ve datos │ Utiliza un canal        │
│ viajan por el MISMO   │ directos; deduce la     │ alternativo (DNS / HTTP)│
│ canal web (HTTP).     │ información observando  │ cuando no hay salida    │
│ Ej: Error / UNION.    │ tiempos o booleanos.    │ directa por la web.     │
└───────────────────────┘ └───────────────────────┘ └───────────────────────┘
```

---

### A. Inyección SQL en Banda (*In-Band SQLi / Classic*)
* **Mecanismo:** Es la forma más directa y común de inyección. El atacante utiliza el **mismo canal de comunicación** (la solicitud HTTP estándar) para introducir el payload malicioso y visualizar los resultados extraídos reflejados directamente en la página web.
* **Subtipos Principales:**
  * **Inyección Basada en Errores (*Error-Based SQLi*):** El atacante introduce caracteres deliberadamente inválidos para forzar al motor de base de datos a arrojar mensajes de error descriptivos que revelen nombres de tablas, columnas o versiones de software.
  * **Inyección Basada en UNION (*UNION-Based SQLi*):** Utiliza el operador `UNION SELECT` para anexar los resultados de una consulta arbitraria a los resultados devueltos por la aplicación web original.

---

### B. Inyección SQL Inferencial (*Inferential SQLi / Blind SQLi*)
* **Mecanismo:** Ocurre cuando la aplicación es vulnerable pero no muestra datos de la base de datos ni mensajes de error en pantalla. El atacante no puede leer los registros directamente, pero puede **reconstruir la información bit a bit analizando el comportamiento del servidor**.
* **Subtipos Principales:**
  * **Ciega Basada en Booleanos (*Boolean-Based Blind*):** El atacante envía consultas que evalúan condiciones lógicas de Verdadero o Falso. Si la condición es Verdadera, la página carga un contenido específico; si es Falsa, la página responde de manera diferente.
  * **Ciega Basada en Tiempo (*Time-Based Blind*):** El atacante inyecta funciones de retardo temporal (ej. `pg_sleep(5)` en PostgreSQL o `WAITFOR DELAY '0:0:5'` en MSSQL). Si la base de datos tarda 5 segundos adicionales en responder, el atacante confirma que su premisa evaluada es correcta.

---

### C. Inyección SQL Fuera de Banda (*Out-of-Band SQLi / OOB*)
* **Mecanismo:** Se utiliza cuando el servidor no devuelve datos directos y el canal web es demasiado inestable para ataques inferenciales. El atacante obliga al servidor de base de datos a realizar una conexión de red externa hacia un servidor bajo su control mediante solicitudes **DNS** o **HTTP** (ej. utilizando utilidades como `UTL_HTTP` en Oracle o `xp_dirtree` en MSSQL).
* **Condición:** Requiere que ciertas funciones avanzadas o permisos de red saliente estén habilitados en el servidor de base de datos.

## 3. Anatomía de un Ataque de Inyección SQL: Evasión de Autenticación

Analicemos cómo un formulario de inicio de sesión programado de forma insegura permite a un atacante acceder como Administrador sin conocer la contraseña:

```
┌──────────────────────────────────────────────────────────────────────────────┐
│                  EJEMPLO DE CÓDIGO VULNERABLE (Concatenación)                │
└──────────────────────────────────────────────────────────────────────────────┘

 $usuario  = $_POST['user'];
 $password = $_POST['pass'];

 // Consulta construida concatenando cadenas de texto sin validar:
 $sql = "SELECT * FROM usuarios WHERE email = '$usuario' AND clave = '$password'";
```

```
┌──────────────────────────────────────────────────────────────────────────────┐
│                       PAYLOAD DE ATAQUE Y EJECUCIÓN                          │
├──────────────────────────────────────────────────────────────────────────────┤
│ 1. El atacante ingresa en el campo Usuario:                                  │
│    admin' OR '1'='1' --                                                      │
│                                                                              │
│ 2. Consulta resultante interpretada por el motor SQL:                        │
│    SELECT * FROM usuarios WHERE email = 'admin' OR '1'='1' --' AND clave = 'x'│
│                                                                              │
│ 3. Mecánica de Ruptura:                                                      │
│    • Las comillas (') cierran prematuramente el campo de texto.              │
│    • El operador OR '1'='1' evalúa a VERDADERO (True) para toda la fila.     │
│    • Los guiones dobles (--) indican un COMENTARIO en SQL, anulando la       │
│      verificación de la contraseña para el resto de la consulta.             │
│                                                                              │
│ 4. Resultado: El servidor autentica al atacante con la cuenta de admin.      │
└──────────────────────────────────────────────────────────────────────────────┘
```

## 4. Metodologías de Prevención y Técnicas de Código Seguro

La prevención efectiva de la inyección SQL no depende de una sola técnica, sino de la aplicación rigurosa de principios de diseño seguro:

```
┌──────────────────────────────────────────────────────────────────────────┐
│                   PILONAS DE PROTECCIÓN CONTRA INYECCIÓN SQL             │
├──────────────────────┬───────────────────────────────────────────────────┤
│ Técnica              │ Descripción y Rol en la Defensa                   │
├──────────────────────┼───────────────────────────────────────────────────┤
│ 1. Sentencias        │ El estándar de oro: separa el código SQL de los   │
│    Preparadas        │ datos suministrados por el usuario.               │
├──────────────────────┼───────────────────────────────────────────────────┤
│ 2. Validación de     │ Verifica que los datos coincidan estrictamente    │
│    Entradas          │ con tipos, formatos y listas blancas (*Allowlist*)│
├──────────────────────┼───────────────────────────────────────────────────┤
│ 3. Saneamiento y     │ Neutraliza caracteres especiales sintácticos      │
│    Escape            │ (comillas, barras, delimitadores).                │
├──────────────────────┼───────────────────────────────────────────────────┤
│ 4. Privilegio Mínimo │ Cuentas de base de datos con permisos estrictos   │
│    en BD (PoLP)      │ (sin permisos de DROP o administración de SO).    │
└──────────────────────┴───────────────────────────────────────────────────┘
```

---

### A. El Estándar Definitivo: Sentencias Preparadas y Consultas Parametrizadas

Las **Sentencias Preparadas (*Prepared Statements*)** o **Consultas Parametrizadas** precompilan la estructura sintáctica de la consulta en el motor de base de datos antes de enlazar los valores del usuario. Los parámetros son tratados estrictamente como **literales de datos**, haciendo imposible que una entrada maliciosa altere la lógica de la consulta.

```
┌──────────────────────────────────────────────────────────────────────────────┐
│                 COMPARATIVA: CÓDIGO INSEGURO VS. CÓDIGO SEGURO               │
├──────────────────────────────────────────────────────────────────────────────┤
│ ❌ CÓDIGO INSEGURO (Vulnerable a Inyección):                                  │
│    $sql = "SELECT * FROM usuarios WHERE email = '" . $_POST['email'] . "'";  │
│    $resultado = $db->query($sql);                                            │
│                                                                              │
│ ✅ CÓDIGO SEGURO (Sentencia Preparada con Parámetros Tipados - PDO):          │
│    $stmt = $db->prepare("SELECT * FROM usuarios WHERE email = :email");      │
│    $stmt->execute([':email' => $_POST['email']]);                            │
│    $resultado = $stmt->fetch();                                              │
└──────────────────────────────────────────────────────────────────────────────┘
```

---

### B. Validación de Entradas y Listas Blancas (*Allowlisting*)
* **Comprobación de Tipos Fuertes:** Si un parámetro de URL espera un identificador numérico de producto (`/producto?id=45`), el backend debe forzar la conversión a tipo entero (`intval($_GET['id'])`) antes de cualquier procesamiento. Si el usuario envía texto o caracteres extraños, la petición se rechaza de inmediato.
* **Listas Blancas para Elementos Dinámicos:** Si una consulta requiere ordenar datos dinámicamente (`ORDER BY columna`), los nombres de las columnas nunca deben tomarse directamente de la entrada del usuario; deben validarse contra una lista predefinida en el backend (ej. `['precio', 'fecha', 'nombre']`).

---

### C. Principio de Privilegio Mínimo en la Base de Datos (PoLP)
* Las aplicaciones web nunca deben conectarse a la base de datos utilizando cuentas con privilegios de superusuario (`root`, `sa` o `SYSDBA`).
* Se deben crear usuarios dedicados por aplicación con permisos limitados exclusivamente a las operaciones requeridas (`SELECT`, `INSERT`, `UPDATE`), revocando privilegios destructivos (`DROP TABLE`, `GRANT`, acceso al sistema de archivos).

## Puntos Clave para Exámenes y Práctica Profesional

> [!IMPORTANT]
> * **Inyección SQL (SQLi):** Ocurre cuando datos no confiables se concatenan en una consulta, alterando su estructura lógica.
> * **Las 3 Categorías:**
>   * **En Banda (*In-Band*):** El ataque y los datos viajan por el mismo canal web (ej. *Error-Based* y *UNION-Based*).
>   * **Inferencial (*Blind*):** No muestra datos directos; se deduce evaluando respuestas booleanas (Verdadero/Falso) o retrasos de tiempo (*Time-Based*).
>   * **Fuera de Banda (*Out-of-Band*):** Exfiltra datos mediante protocolos externos (DNS/HTTP) cuando la salida web está bloqueada.
> * **Defensa Principal:** **Sentencias Preparadas (*Prepared Statements*) / Consultas Parametrizadas**, que tratan la entrada del usuario estrictamente como datos literales y nunca como código ejecutable.
> * **Defensas Complementarias:** Validación estricta de entradas (listas blancas y tipado fuerte), saneamiento y privilegio mínimo en cuentas de base de datos.
