# Seguridad y Vulnerabilidades en Canalizaciones CI/CD: De DevOps a DevSecOps

En esta guía exhaustiva del **Curso 5: Activos, Amenazas y Vulnerabilidades**, se analiza en profundidad la arquitectura de las **canalizaciones de Integración Continua, Entrega Continua y Despliegue Continuo (CI/CD)**, las ventajas de incorporar seguridad automatizada (*Shift-Left*), las **cinco vulnerabilidades críticas** que amenazan la cadena de suministro de software, las metodologías de análisis (**SAST**, **DAST**, **SCA** e **IaC**), la **gestión segura de secretos**, y las mejores prácticas de **endurecimiento** (*Hardening*) para proteger los entornos de compilación.

---

## 1. Fundamentos de las Canalizaciones CI/CD

## 2. La Transformación DevSecOps: Integrando Seguridad en el Pipeline

El modelo tradicional de desarrollo evaluaba la seguridad al final del proyecto (justo antes del lanzamiento), generando cuellos de botella y costos astronómicos de corrección. El enfoque **DevSecOps** promueve el principio de **"Shift-Left"** (mover la seguridad hacia la izquierda), incorporando pruebas automáticas de seguridad desde las fases iniciales de desarrollo.

```
┌──────────────────────────────────────────────────────────────────────────────┐
│                    EL FLUJO DE SEGURIDAD AUTOMATIZADA (DevSecOps)            │
└──────────────────────────────────────────────────────────────────────────────┘

 [CÓDIGO FUENTE] ──► [SAST + SCA] ──► [BUILD SEGURO] ──► [DAST + IaC] ──► [PRODUCCIÓN]
      │                     │                │                 │                │
      ▼                     ▼                ▼                 ▼                ▼
   Escaneo de           Detección de      Firma de        Pruebas en       Monitoreo
   Secretos             Vulnerabilidades  Contenedores    Tiempo Real      Continuo
  (GitLeaks)           (Snyk / Sonar)    (Cosign)        (ZAP / DAST)     (SIEM / SOC)
```

### Tecnologías de Análisis de Seguridad en CI/CD:

```
┌──────────────────────────────────────────────────────────────────────────┐
│                   METODOLOGÍAS DE PRUEBAS DE SEGURIDAD                   │
├───────────────────┬──────────────────────────────┬───────────────────────┤
│     1. SAST       │            2. SCA            │        3. DAST        │
│    (Estático)     │        (Composición)         │       (Dinámico)      │
├───────────────────┼──────────────────────────────┼───────────────────────┤
│ Analiza el CÓDIGO │ Examina las DEPENDENCIAS     │ Evalúa la aplicación  │
│ FUENTE en reposo  │ externas y bibliotecas de    │ EN EJECUCIÓN          │
│ (sin ejecutarlo). │ código abierto (Open Source).│ (simula ataques caja  │
│                   │                              │ negra en tiempo real).│
│ Ej: Inyecciones   │ Ej: Detección de CVEs en     │ Ej: Autenticación,    │
│ SQL, XSS, fallos  │ librerías npm, PyPI, Maven o │ fugas de memoria y    │
│ de lógica.        │ imágenes base de Docker.     │ cabeceras HTTP.       │
└───────────────────┴──────────────────────────────┴───────────────────────┘
```

1. **SAST (*Static Application Security Testing*):** Herramientas que inspeccionan el código línea por línea buscando malas prácticas criptográficas, inyecciones de comandos o desbordamientos de búfer antes de generar el binario.
2. **SCA (*Software Composition Analysis*):** Analiza el árbol de dependencias del proyecto comparándolo con bases de datos públicas de vulnerabilidades (**NVD / CVE**) para alertar sobre componentes obsoletos o comprometidos (*ej. Dependabot, Snyk, OWASP Dependency-Check*).
3. **DAST (*Dynamic Application Security Testing*):** Ataca la aplicación desplegada en un entorno de pruebas (*Staging*) desde el exterior para identificar debilidades en los mecanismos de autenticación, control de sesiones y llamadas a APIs.
4. **Validación de Infraestructura como Código (IaC Security):** Análisis automatizado de plantillas *Terraform*, *Kubernetes YAML* o *Dockerfiles* para prevenir contenedores ejecutándose como `root` o puertos administrativos abiertos a Internet (*ej. Checkov, Trivy*).

## 3. Las Cinco Vulnerabilidades Críticas en Canalizaciones CI/CD

Una canalización CI/CD automatiza todo; por lo tanto, **un error en su configuración automatiza la introducción de vulnerabilidades a escala masiva**.

┌──────────────┐ ┌──────────────┐ ┌──────────────┐ ┌──────────────┐ ┌──────────────┐

### Detalle Técnico de las Vulnerabilidades y sus Mitigaciones:

| Vulnerabilidad | Descripción del Riesgo | Escenario de Ataque | Mitigación Técnica Requerida |
| :--- | :--- | :--- | :--- |
| **1. Dependencias Inseguras (*Supply Chain*)** | Uso de bibliotecas de terceros que contienen vulnerabilidades conocidas (**CVEs**) o paquetes maliciosos inyectados por atacantes (*Typosquatting*). | Un atacante compromete un paquete popular en `npm` o `PyPI`. Al compilar el software, el pipeline descarga la versión maliciosa e infecta el producto final. | • Implementar herramientas **SCA** automáticas (**Dependabot**, **Snyk**).<br>• Fijar versiones en archivos de bloqueo (`package-lock.json`, `Pipfile.lock`).<br>• Usar repositorios de artefactos privados proxy con análisis previo. |
| **2. Permisos y Accesos Mal Configurados** | Ausencia de **Control de Acceso Basado en Roles (RBAC)** y privilegios excesivos otorgados a usuarios o tokens del pipeline en repositorios de código. | Un desarrollador con permisos de administrador o una cuenta comprometida modifica el archivo de pipeline `.github/workflows/deploy.yml` para exfiltrar datos o deshabilitar pruebas de seguridad. | • Aplicar el **Principio de Privilegio Mínimo (PoLP)** en cuentas de servicio y desarrolladores.<br>• Exigir **MFA obligatorio** y protección de ramas maestras (*Branch Protection*) con revisión de código obligatoria por pares. |
| **3. Falta de Pruebas de Seguridad Automatizadas** | Desplegar software sin compuertas de seguridad (*Quality Gates*), omitiendo análisis SAST/DAST/SCA en el pipeline. | Se publican a producción aplicaciones con fallos críticos (ej. inyecciones SQL o autenticación rota) que pasan desapercibidos hasta ser explotados por cibercriminales. | • Integrar escaneos **SAST** y **SCA** en cada *Pull Request*.<br>• Configurar **Quality Gates** que bloqueen automáticamente la compilación si se detectan vulnerabilidades de severidad Alta o Crítica. |
| **4. Secretos y Credenciales Expuestas** | Inclusión en texto plano (*Hardcoding*) de claves de API, contraseñas de bases de datos, tokens de AWS/GCP o certificados en el código o en los scripts `.yml`. | El código es subido a un repositorio público o un atacante con acceso de lectura roba las credenciales de la base de datos de producción incrustadas en el script. | • **Prohibición absoluta** de almacenar secretos en código.<br>• Utilizar bóvedas de secretos dedicadas (**HashiCorp Vault**, **AWS Secrets Manager**, **GitHub Encrypted Secrets**).<br>• Escaneo preventivo de código pre-commit (**GitLeaks**, **TruffleHog**). |
| **5. Entornos de Compilación Inseguros (*Insecure Runners*)** | Servidores de compilación persistentes (*Self-Hosted Runners*) sin parches, compartidos entre proyectos o con privilegios elevados de `root`/`sudo`. | Un atacante aprovecha una compilación para escapar del contenedor de prueba, persistir en el servidor de compilación y modificar binarios de otros proyectos corporativos. | • Utilizar **ejecutores efímeros (*Ephemeral Runners*)** basados en contenedores que se destruyen al finalizar cada trabajo.<br>• Aislar la red del entorno de compilación de la red corporativa interna. |

## 4. Estrategia de Defensa en Profundidad para CI/CD

Construir una canalización resiliente exige articular salvaguardas en todas las capas del ciclo de entrega de software:

```
┌──────────────────────────────────────────────────────────────────────────────┐
│               PILONAS DE UNA ESTRATEGIA SEGURA DE CI/CD                      │
└──────────────────────────────────────────────────────────────────────────────┘

 1. GOBERNANZA Y ACCESOS    ➔ RBAC estricto, MFA obligatorio, protección de ramas.
 2. BÓVEDAS DE SECRETOS     ➔ HashiCorp Vault / Secrets Manager con rotación continua.
 3. COMPUERTAS DE SEGURIDAD ➔ SAST + SCA + DAST que detienen builds vulnerables.
 4. INTEGRIDAD DE ARTEFACTOS➔ Firma criptográfica de código y contenedores (Sigstore).
 5. EJECUTORES EFÍMEROS     ➔ Aislamiento total de entornos de compilación.
```

## Puntos Clave para Exámenes y Práctica Profesional

> [!IMPORTANT]
> * **Definición CI/CD:** **CI** automatiza compilación y pruebas unitarias; **CD (Delivery)** prepara el código para producción con visto bueno manual; **CD (Deployment)** publica automáticamente en producción sin intervención humana.
> * **Enfoque DevSecOps (*Shift-Left*):** La seguridad se integra desde las primeras líneas de código mediante automatización continua.
> * **Tríada de Análisis:** **SAST** (código fuente estático), **SCA** (librerías y CVEs de terceros) y **DAST** (aplicación viva en tiempo de ejecución).
> * **Gestión de Secretos:** Nunca codificar claves o tokens en código; utilizar siempre bóvedas cifradas con inyección de variables en tiempo de ejecución.
> * **Infraestructura Efímera:** Los ejecutores de compilación deben ser aislados y destruirse tras cada ejecución para evitar la contaminación cruzada o persistencia de atacantes.
