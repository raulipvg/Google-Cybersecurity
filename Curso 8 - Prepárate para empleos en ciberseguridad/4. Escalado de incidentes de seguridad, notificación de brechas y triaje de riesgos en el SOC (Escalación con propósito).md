# Escalado de Incidentes de Seguridad, Notificación de Brechas y Triaje de Riesgos en el SOC (Escalación con Propósito)

En esta cuarta entrega del **Curso 8: Prepárate para empleos en ciberseguridad**, se aborda una de las responsabilidades operativas más determinantes para un analista de seguridad en su transición al entorno corporativo: el **escalado de incidentes de seguridad (*Incident Escalation*)**. En las operaciones de un Centro de Operaciones de Seguridad (SOC), la eficacia de la defensa no se mide únicamente por la capacidad de detectar anomalías, sino por la disciplina y celeridad con la que se transfiere un incidente al personal o departamento adecuado. Se profundiza en la **escalación con un propósito**, las **leyes internacionales de notificación de brechas de datos (PII/SPII)**, la diferenciación técnica entre **problemas de bajo nivel y amenazas críticas**, las **matrices y árboles de escalado**, y el impacto legal y financiero derivado de fallar en la elevación oportuna de una alerta.

---

## 1. Fundamentos del Escalado de Incidentes (*Incident Escalation*)

El **escalado de incidentes** es el proceso formal y sistemático mediante el cual una alerta, anomalía o potencial compromiso de seguridad es identificado, documentado y transferido vertical u horizontalmente a un analista con mayor experiencia, a un equipo de respuesta especializada (CIRT/CSIRT) o a los líderes de la organización.

```
┌───────────────────────────────────────────────────────────────────────────────────────────┐
│                    JERARQUÍA Y FLUJO DE ESCALADO EN EL SOC (TIER MODEL)                   │
└─────────────────────────────────────────────┬─────────────────────────────────────────────┘
                                              │
 ┌──────────────────────────────────────┐     │     ┌──────────────────────────────────────┐
 │          TIER 1 (Triage)             │ ───┼───► │  TIER 2 (Respuesta a Incidentes / DF)│
 │ - Monitoreo de alertas SIEM / EDR    │     │     │ - Análisis forense en profundidad    │
 │ - Descarte de falsos positivos       │     │     │ - Contención y aislamiento de hosts  │
 │ - Enriquecimiento inicial de datos   │     │     │ - Erradicación de malware avanzado   │
 └──────────────────┬───────────────────┘     │     └──────────────────┬───────────────────┘
                    │ (Supera Umbral)         │                        │ (Incidente Severo)
                    ▼                         │                        ▼
 ┌──────────────────────────────────────┐     │     ┌──────────────────────────────────────┐
 │       POLÍTICA DE ESCALADO           │     │     │      TIER 3 / CSIRT / LIDERAZGO      │
 │ Criterios predefinidos:              │     │     │ - Caza de amenazas (Threat Hunting)  │
 │ ¿Involucra PII? ¿Fuerza bruta activa?│     │     │ - Notificación legal de brechas      │
 │ ¿Software no autorizado malicioso?   │     │     │ - Comunicación CISO / Alta Dirección │
 └──────────────────────────────────────┘     │     └──────────────────────────────────────┘
```

### ¿Qué Significa "Escalar con un Propósito"?
Escalar no consiste en transferir un ticket para eludir responsabilidades de triaje. **Escalar con propósito** significa que el analista de Nivel 1 (Tier 1):
1. Ha verificado que la alerta no es un falso positivo mediante correlación de telemetría.
2. Ha recopilado y contextualizado los artefactos clave (direcciones IP, nombres de host, cuentas de usuario, marcas de tiempo e indicadores de compromiso - IoCs).
3. Identifica claramente **por qué** el incidente excede sus permisos o capacidades de contención técnica.
4. Entrega el caso con un informe preliminar claro que permite a los respondedores senior actuar inmediatamente sin reiniciar la investigación desde cero.

## 2. Leyes de Notificación de Brechas (*Breach Notification Laws*)

Uno de los factores que convierte el escalado oportuno en un imperativo legal son las **leyes de notificación de brechas de seguridad**. En la gran mayoría de las jurisdicciones, las organizaciones tienen la obligación jurídica de notificar formalmente a los individuos afectados y a los entes reguladores cuando se produce una exposición no autorizada de **Información de Identificación Personal (PII)** o datos sensibles.

```
┌───────────────────────────────────────────────────────────────────────────────────────────┐
│                       LEGISLACIÓN GLOBAL DE NOTIFICACIÓN DE BRECHAS                       │
├────────────────────┬──────────────────────────────────┬──────────────────────────────────┤
│ Marco Legal        │ Ámbito y Jurisdicción            │ Plazos y Condiciones de Alerta   │
├────────────────────┼──────────────────────────────────┼──────────────────────────────────┤
│ **GDPR** (Art. 33) │ Unión Europea / Ciudadanos UE    │ **72 Horas** tras tener constan- │
│                    │ (Reglamento General de Datos)    │ cia ante la Autoridad de Control │
├────────────────────┼──────────────────────────────────┼──────────────────────────────────┤
│ **Leyes Estatales  │ Estados Unidos (50 Estados,      │ Plazos variables (desde "sin de- │
│ de EE.UU.**        │ ej. CCPA California, NY SHIELD)  │ mora indebida" hasta 30-45 días) │
├────────────────────┼──────────────────────────────────┼──────────────────────────────────┤
│ **HIPAA Breach     │ Sector Salud / EE.UU.            │ Máximo 60 días naturales (inme-  │
│ Notification**     │ (Protección de PHI)              │ diato si afecta a > 500 personas)│
├────────────────────┼──────────────────────────────────┼──────────────────────────────────┤
│ **PCI-DSS**        │ Global / Pasarelas de Pago       │ Notificación inmediata a marcas  │
│                    │ (Datos de Tarjetas de Pago)      │ de tarjetas y bancos adquirentes │
└────────────────────┴──────────────────────────────────┴──────────────────────────────────┘
```

> [!IMPORTANT]
> **El "Reloj Regulatorio" y la Responsabilidad del Analista:**
> Los plazos legales de notificación (como las **72 horas del GDPR**) comienzan a correr en el momento exacto en que la organización *adquiere conocimiento fundado* de la brecha. Si un analista junior detecta una exfiltración de PII pero no la escala adecuadamente durante dos días, está consumiendo el 66% de la ventana de cumplimiento legal de la empresa, lo que puede provocar multas regulatorias millonarias por encubrimiento involuntario o negligencia.

### Tipos de PII que Activan las Leyes de Notificación:
* Números de Seguro Social (SSN), DNI o números de pasaporte.
* Números de licencia de conducir o identificaciones estatales.
* Registros médicos, historiales clínicos e información de seguros de salud (**PHI**).
* Credenciales de acceso financieras (números de cuenta bancaria con claves, números de tarjetas de pago con CVV).

## 3. Taxonomía de Incidentes: Problemas de Bajo Nivel vs. Amenazas Críticas

En el SOC, la mayoría de los eventos diarios son ruidos de fondo o incidentes menores. El desafío crítico para el analista consiste en reconocer **el punto de inflexión (*Tipping Point*)** donde un problema de bajo nivel muta en una amenaza que requiere escalado inmediato.

```
┌──────────────────────────────────────────────────────────────────────────────────────────┐
│                   DIFERENCIACIÓN: BAJO NIVEL vs. INCIDENTE ESCALABLE                     │
├───────────────────────────────┬──────────────────────────────┬───────────────────────────┤
│ Escenario                     │ Problema de Bajo Nivel       │ Indicador de Escalado     │
│                               │ (Monitoreo / Registro)       │ Inmediato (Peligro Real)  │
├───────────────────────────────┼──────────────────────────────┼───────────────────────────┤
│ **Autenticación Fallida**     │ Un empleado falla 2 o 3      │ **15 fallos en 30 minutos**│
│                               │ intentos por olvido de clave │ (Ataque de fuerza bruta o │
│                               │ o teclado desconfigurado.    │ password spraying masivo).│
├───────────────────────────────┼──────────────────────────────┼───────────────────────────┤
│ **Software no Autorizado**    │ Usuario descarga una herra-  │ El software descargado es │
│ (*Shadow IT*)                 │ mienta no aprobada para com- │ un ejecutable troyanizado │
│                               │ primir archivos sin malware. │ que conecta a una IP C2.  │
├───────────────────────────────┼──────────────────────────────┼───────────────────────────┤
│ **Acceso a Archivos**         │ Un usuario intenta abrir un  │ Acceso masivo a carpetas  │
│                               │ recurso compartido sin permi-│ compartidas con cifrado   │
│                               │ sos por error de enlace.     │ repentino (Ransomware).   │
├───────────────────────────────┼──────────────────────────────┼───────────────────────────┤
│ **Tráfico de Red**            │ Petición DNS aislada a un    │ Balizamiento (*beaconing*)│
│                               │ dominio con baja reputación. │ regular cada 60s hacia un │
│                               │                              │ Dominio Recién Registrado.│
└───────────────────────────────┴──────────────────────────────┴───────────────────────────┘
```

### 3.1. Caso 1: Intentos Excesivos de Inicio de Sesión
* **Comportamiento Ordinario:** Un empleado ingresa mal su clave un par de veces por la mañana. Se resuelve mediante el autoservicio de contraseñas.
* **Comportamiento Anómalo Escalable:** Un script automatizado intenta autenticarse contra la cuenta del empleado 15 veces en 30 minutos, utilizando contraseñas comunes del diccionario *RockYou*, o intentos continuos procedentes de una dirección IP geográficamente distante (ej. acceso desde Rusia 10 minutos después de un acceso local). **Acción:** Bloqueo de cuenta preventivo y escalado a Tier 2.

### 3.2. Caso 2: Software No Autorizado y Malware
* **Comportamiento Ordinario:** Un desarrollador descarga una versión portátil de un editor de texto. Viola la política de TI, pero el hash es limpio en VirusTotal.
* **Comportamiento Anómalo Escalable:** Un empleado descarga un juego gratuito o un convertidor de PDF de una página dudosa. El archivo binario contiene un **troyano de acceso remoto (RAT)** que desactiva el servicio de antivirus, inyecta código en `explorer.exe` y comienza a realizar reconocimiento interno en la red. **Acción:** Aislamiento inmediato del endpoint de la red y escalado al equipo de respuesta forense.

## 4. El Proceso de Elevación: Políticas, Árboles y Canales de Comunicación

Toda organización madura posee una **Política de Escalado de Incidentes** documentada que elimina la improvisación durante las crisis.

```
┌───────────────────────────────────────────────────────────────────────────────────────────┐
│                    ÁRBOL DE DECISIÓN Y ESCALADO EN EL SOC (INCIDENT TREE)                 │
└─────────────────────────────────────────────┬─────────────────────────────────────────────┘
                                              │
                                ┌─────────────▼─────────────┐
                                │ ALERTA DETECTADA EN SIEM  │
                                └─────────────┬─────────────┘
                                              │
                                              ▼
                             ¿Es Falso Positivo Comprobado?
                                    ├── SÍ ──► Cerrar ticket con evidencia
                                    └── NO ──► ¿Afecta a datos de PII/SPII o
                                               sistemas de alta criticidad?
                                                    ├── NO ──► Investigar Tier 1
                                                    └── SÍ ──► ¡ACTIVAR ESCALADO!
                                                                    │
                                   ┌────────────────────────────────┴────────────────┐
                                   ▼                                                 ▼
                      ┌─────────────────────────┐                       ┌─────────────────────────┐
                      │ CANAL PRIMARIO (SLA: 15m│                       │ SI CONTACTO NO RESPONDE │
                      │ Contactar Líder de Turno│                       │ (Mecanismo Failover):   │
                      │ vía Ticket / Chat SOC   │                       │ Contactar Gerente CISO  │
                      └─────────────────────────┘                       └─────────────────────────┘
```

### 4.1. Componentes de la Política de Escalado:
1. **Matriz de Contactos Primarios y Secundarios (*Escalation Contacts*):** Define a quién se notifica según el tipo de incidente (ej. intrusión de red $\rightarrow$ Equipo de Redes/SOC; fuga de datos de empleados $\rightarrow$ SOC + Recursos Humanos + Legal).
2. **Protocolo de Respaldo (*Failover Mechanism*):** Si el líder del turno o el primer respondedor no acusa recibo del escalado en un tiempo prefijado (ej. 15 minutos), el procedimiento exige contactar automáticamente al subdirector o al CISO.
3. **Canales de Elevación:**
   * **Sistemas de Gestión de Tickets (ITSM / SOAR):** Herramientas como ServiceNow, Jira Service Management o TheHive para mantener la cadena de custodia y la trazabilidad formal.
   * **Comunicaciones Fuera de Banda (*Out-of-Band* - OOB):** Canales de mensajería seguros y cifrados (Signal, teléfonos satelitales, instancias aisladas de Teams) si se sospecha que el atacante tiene acceso al correo corporativo interno.

## 5. El Impacto Devastador de No Escalar Oportunamente

Omitir o demorar el escalado de un incidente genera consecuencias severas que trascienden el ámbito tecnológico:

```
┌───────────────────────────────────────────────────────────────────────────────────────────┐
│                        EFECTO DE LA OMISIÓN DEL ESCALADO TEMPRANO                         │
└─────────────────────────────────────────────┬─────────────────────────────────────────────┘
                                              │
 ┌──────────────────────┐         ┌───────────▼───────────┐         ┌──────────────────────┐
 │ FALTA DE ESCALADO    │────────►│ MOVIMIENTO LATERAL    │────────►│ CIFRADO DE BACKUPS Y │
 │ Analista ignora      │         │ El atacante pasa del  │         │ EXFILTRACIÓN DE PII  │
 │ 15 logins fallidos   │         │ endpoint a los DCs    │         │ (Desastre total)     │
 └──────────────────────┘         └───────────────────────┘         └──────────┬───────────┘
                                                                               │
                                  ┌───────────────────────┐                    │
                                  │ SANCIONES LEGALES,    │◄───────────────────┘
                                  │ PÉRDIDA DE CLIENTES   │
                                  │ Y QUIEBRA DEL NEGOCIO │
                                  └───────────────────────┘
```

1. **Ampliación del Radio de Explosión (*Blast Radius*):** Una infección aislada en una estación de trabajo que pudo contenerse en 10 minutos se propaga a servidores de bases de datos mediante movimiento lateral (*lateral movement*) y escalada de privilegios.
2. **Pérdida de Evidencia Volátil:** La demora en el escalado permite que los registros en memoria RAM se sobrescriban o que el atacante limpie los logs de eventos del sistema (`wevtutil cl`).
3. **Pérdida de Reputación y Fuga de Clientes:** Descubrir una brecha a través de la prensa o de un cliente externo en lugar de detectarla internamente destruye la confianza institucional.

## 6. Laboratorio Práctico: Motor de Evaluación y Escalado Automático en Python

El siguiente script implementa la lógica de un motor de correlación en un SIEM o plataforma SOAR que evalúa eventos de bajo nivel, detecta cuándo superan los umbrales de seguridad y genera una orden formal de escalado con determinación de criticidad y plazos regulatorios:

```python
"""
soc_escalation_engine.py - Motor de Evaluación y Escalado de Incidentes
Autor: Equipo del SOC / Formación de Analistas
Propósito: Evaluar eventos sospechosos, detectar umbrales críticos y activar escalado formal.
"""

from datetime import datetime, timezone
from typing import Dict, List, Optional

# Definición de la Política Corporativa de Escalado
ESCALATION_POLICY = {
    "login_threshold_count": 5,        # Máximo de intentos fallidos antes de alertar
    "login_time_window_minutes": 30,    # Ventana de tiempo evaluada
    "dangerous_extensions": [".exe", ".ps1", ".bat", ".vbs", ".dll"],
    "sla_escalation_minutes": {
        "CRITICAL": 15,
        "HIGH": 30,
        "MEDIUM": 60,
        "LOW": 240
    }
}

# Simulación de Eventos Registrados en el SIEM
TELEMETRY_EVENTS = [
    {
        "event_id": "EVT-101",
        "type": "FAILED_LOGIN",
        "user": "rhernandez",
        "failed_attempts": 15,
        "window_minutes": 25,
        "source_ip": "185.220.101.5", # IP de salida Tor conocida
        "involves_pii_repo": True
    },
    {
        "event_id": "EVT-102",
        "type": "FILE_DOWNLOAD",
        "user": "mlopez",
        "filename": "annual_bonus_calculator.exe",
        "source_url": "http://nrd-suspicious-domain.xyz/tool.exe",
        "involves_pii_repo": False
    },
    {
        "event_id": "EVT-103",
        "type": "FAILED_LOGIN",
        "user": "jdoe",
        "failed_attempts": 2,
        "window_minutes": 10,
        "source_ip": "10.0.1.25",
        "involves_pii_repo": False
    }
]

def evaluate_and_escalate(event: Dict[str, any]) -> Optional[Dict[str, any]]:
    """
    Evalúa si un evento de telemetría supera los umbrales de bajo nivel
    y construye un paquete formal de escalado.
    """
    requires_escalation = False
    severity = "LOW"
    escalation_reason = ""
    target_team = "Tier 1 Internal"

    # Regla 1: Intentos excesivos de autenticación (Fuerza Bruta)
    if event["type"] == "FAILED_LOGIN":
        attempts = event["failed_attempts"]
        window = event["window_minutes"]
        if attempts >= ESCALATION_POLICY["login_threshold_count"] and window <= ESCALATION_POLICY["login_time_window_minutes"]:
            requires_escalation = True
            if event.get("involves_pii_repo", False):
                severity = "CRITICAL"
                escalation_reason = f"Ataque de fuerza bruta ({attempts} fallos en {window}m) contra repositorio con PII."
                target_team = "Tier 2 IR + DPO / Legal (GDPR 72h)"
            else:
                severity = "HIGH"
                escalation_reason = f"Fuerza bruta detectada ({attempts} intentos fallidos en {window}m)."
                target_team = "Tier 2 Incident Response"

    # Regla 2: Descarga de ejecutables sospechosos por empleados
    elif event["type"] == "FILE_DOWNLOAD":
        filename = event["filename"]
        if any(filename.endswith(ext) for ext in ESCALATION_POLICY["dangerous_extensions"]):
            requires_escalation = True
            severity = "HIGH"
            escalation_reason = f"Descarga de binario no autorizado potencialmente malicioso: '{filename}'."
            target_team = "Tier 2 Endpoint Protection / Malware Analysis"

    if not requires_escalation:
        return None

    # Estructuración del Paquete de Escalado Formal
    return {
        "ticket_id": f"ESC-{event['event_id']}",
        "timestamp_utc": datetime.now(timezone.utc).isoformat(),
        "severity": severity,
        "affected_user": event["user"],
        "assigned_team": target_team,
        "sla_response_limit_min": ESCALATION_POLICY["sla_escalation_minutes"][severity],
        "reason": escalation_reason,
        "evidence_metadata": event
    }


print("=" * 80)
print("      MOTOR DE CORRELACIÓN Y ESCALADO FORMAL DE INCIDENTES (SOC TIER 1)     ")
print("=" * 80)

for evt in TELEMETRY_EVENTS:
    escalation_ticket = evaluate_and_escalate(evt)
    if escalation_ticket:
        print(f"\n[!] ALERTA CRÍTICA - ESCALADO ACTIVADO: {escalation_ticket['ticket_id']}")
        print(f"    - Severidad Asignada    : {escalation_ticket['severity']}")
        print(f"    - Usuario Involucrado   : {escalation_ticket['affected_user']}")
        print(f"    - Equipo Notificado     : {escalation_ticket['assigned_team']}")
        print(f"    - SLA Respuesta Máxima  : {escalation_ticket['sla_response_limit_min']} minutos")
        print(f"    - Causa del Escalado    : {escalation_ticket['reason']}")
    else:
        print(f"\n[i] Evento {evt['event_id']} ({evt['user']}): Actividad dentro de umbrales normales (Sin escalado).")

print("\n" + "=" * 80)
```

## 7. Resumen y Puntos Clave

1. **Definición de Escalado:** Proceso formal de transferir incidentes potenciales a miembros del equipo con mayor nivel técnico o liderazgo, garantizando contención y cumplimiento.
2. **Escalar con Propósito:** No transferir tickets a ciegas; enriquecer la alerta con contexto, descartar falsos positivos y delimitar claramente el motivo de la elevación.
3. **Leyes de Notificación de Brechas:**
   * Obligación legal de notificar exposiciones de **PII**, datos médicos (**PHI**) o financieros.
   * Marcos como el **GDPR exigen notificación en un plazo improrrogable de 72 horas**. Omitir el escalado temprano agota este plazo y desencadena sanciones severas.
4. **Umbrales entre Bajo Nivel y Amenaza Real:**
   * 1 o 2 contraseñas erróneas son habituales; **15 intentos en 30 minutos** representan un ataque de fuerza bruta que exige escalado inmediato.
   * Software no aprobado ordinario requiere políticas de TI; software con ejecutables sospechosos (.exe, .ps1) representa posible infección de malware troyanizado.
5. **Estructura de la Política de Escalado:** Cada organización establece canales claros (tickets, comunicación OOB), contactos primarios y **mecanismos de respaldo (*failover*)** en caso de que el primer respondedor no esté disponible.
