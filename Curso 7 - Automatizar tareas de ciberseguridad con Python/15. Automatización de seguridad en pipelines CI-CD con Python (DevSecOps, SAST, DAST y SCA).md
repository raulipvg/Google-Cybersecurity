# Automatización de Seguridad en Pipelines CI/CD con Python (DevSecOps, SAST, DAST y SCA)

En esta decimoquinta entrega del **Curso 7: Automatizar tareas de ciberseguridad con Python**, se analiza la convergencia entre el desarrollo de software, la infraestructura y la seguridad operativa: el paradigma **DevSecOps**. A medida que las organizaciones adoptan canalizaciones de **Integración Continua y Entrega/Despliegue Continuo (CI/CD)** para acelerar el ciclo de vida del software, la seguridad manual se convierte en un cuello de botella ineficiente y propenso a fallos. Python se posiciona como el lenguaje estándar de la industria para orquestar compuertas de seguridad (*Security Quality Gates*), interactuar con APIs de herramientas de escaneo, auditar dependencias de terceros y aplicar el principio de **Política como Código (*Policy as Code*)** para bloquear vulnerabilidades antes de que alcancen entornos productivos.

## 1. El Paradigma DevSecOps y el Principio Shift-Left

Tradicionalmente, las auditorías de seguridad se ejecutaban al final del ciclo de vida del desarrollo de software (fase de prelanzamiento), lo que generaba fricción entre los equipos de desarrollo y seguridad, además de costes exorbitantes al mitigar fallos de diseño ya implementados.

```
┌───────────────────────────────────────────────────────────────────────────────────────────┐
│                       EVOLUCIÓN HACIA LA SEGURIDAD "SHIFT-LEFT"                           │
└─────────────────────────────────────────────┬─────────────────────────────────────────────┘
                                              │
  TRADICIONAL (Inspección Tardía):            │  DEVSECOPS (Seguridad Continua "Shift-Left"):
  ┌──────────┐   ┌──────────┐   ┌──────────┐  │  ┌─────────────────────────────────────────┐
  │ Plan &   │──►│ Build &  │──►│ Auditoría│  │  │ Plan ──► Commit ──► Build ──► Test ──► Deploy│
  │ Codifica │   │ Despliega│   │ de Seg.  │  │  │  │         │         │        │         │   │
  └──────────┘   └──────────┘   └────┬─────┘  │  │  ▼         ▼         ▼        ▼         ▼   │
                                     │        │  │ Modelado  Pre-commit  SAST     DAST    Sec  │
                         Vulnerabilidad en    │  │ Amenazas   Linters    SCA    Sandboxing Ops │
                         PRODUCCIÓN (Coste:   │  └─────────────────────────────────────────┘
                         30x - 100x)          │   Detección Temprana con Python (Coste: 1x)
```

### 1.1. ¿Por qué Python en Pipelines CI/CD?
1. **Velocidad y Agilidad de Ejecución:** Los scripts de Python se ejecutan como pasos nativos de un runner de CI/CD sin requerir compilación previa.
2. **Ecosistema Especializado de Seguridad:** Herramientas de análisis de vulnerabilidades (`bandit`, `pip-audit`, `safety`, `trivy`, `semgrep`) disponen de interfaces nativas o APIs en Python.
3. **Consistencia Forense:** Automatizar las verificaciones mediante código elimina la variabilidad del factor humano, asegurando que cada *commit* o *pull request* sea evaluado con las mismas reglas.
4. **Interoperabilidad Universal:** Mediante bibliotecas como `requests`, `urllib` y `json`, Python interactúa con cualquier API REST de servidores CI/CD (Jenkins, GitLab CI, GitHub Actions, CircleCI) o plataformas de ticketing y mensajería (Jira, Slack, Microsoft Teams).

## 2. Pilares de Pruebas de Seguridad Automatizadas en CI/CD

El núcleo de un pipeline DevSecOps automatizado con Python abarca tres metodologías complementarias de análisis de seguridad:

```
┌───────────────────────────────────────────────────────────────────────────────────────────┐
│                   METODOLOGÍAS DE PRUEBAS AUTOMATIZADAS EN EL PIPELINE                    │
├────────────────────────────┬─────────────────────────────┬────────────────────────────────┤
│ SAST (Static Testing)      │ DAST (Dynamic Testing)      │ SCA (Composition Analysis)     │
├────────────────────────────┼─────────────────────────────┼────────────────────────────────┤
│ Código fuente en reposo    │ Aplicación en ejecución     │ Dependencias de terceros       │
│ Analiza AST y patrones     │ Pruebas de caja negra       │ Compara con bases CVE / NVD    │
│ Prevención pre-build       │ Pruebas en staging/sandbox  │ Previene riesgos supply chain  │
│ Herramientas: Bandit       │ Herramientas: OWASP ZAP     │ Herramientas: pip-audit, safety│
└────────────────────────────┴─────────────────────────────┴────────────────────────────────┘
```

---

### 2.1. SAST (Static Application Security Testing)
Las pruebas estáticas examinan el código fuente directamente, sin ejecutar el programa. Buscan patrones de codificación insegura, llamadas a funciones deprecadas o vulnerabilidades lógicas.

* **Herramienta Nativa Python:** `Bandit`. Es un linter de seguridad que construye el Árbol de Sintaxis Abstracta (AST) del código fuente y aplica plugins de comprobación contra fallos comunes (CWEs) como inyección SQL, uso inseguro de `eval()`, deserialización con `pickle` y contraseñas fijadas en texto plano (*hardcoded secrets*).
* **Rol de Python en el Pipeline:** Ejecutar la herramienta en modo silencioso emitiendo un reporte JSON, parsear los hallazgos por severidad (`HIGH`, `MEDIUM`, `LOW`) y bloquear el flujo si se detectan vulnerabilidades críticas.

```bash
# Ejecución típica de Bandit en un paso de CI emitiendo reporte estructurado
bandit -r ./src -f json -o bandit_report.json
```

---

### 2.2. DAST (Dynamic Application Security Testing)
Las pruebas dinámicas evalúan la aplicación cuando ya se encuentra compilada, empaquetada y desplegada en un entorno de pruebas aislado (*sandbox* o *staging*).

* **Enfoque de Caja Negra:** El escáner simula peticiones maliciosas externas como inyecciones SQL en parámetros HTTP, Cross-Site Scripting (XSS), inclusión remota de archivos (LFI/RFI) y mala configuración de cabeceras de respuesta (`Content-Security-Policy`, `Strict-Transport-Security`).
* **Rol de Python en el Pipeline:** Utilizar el cliente de API oficial de **OWASP ZAP** (`zap-cli` o `python-owasp-zap-v2.4`) para encender la aplicación, ejecutar un spider web que mapee los endpoints, lanzar un escaneo activo y recopilar las vulnerabilidades encontradas.

---

### 2.3. SCA (Software Composition Analysis)
Las aplicaciones modernas están compuestas entre un 70% y un 90% por librerías y componentes de terceros de código abierto (*open-source*). Los ataques a la cadena de suministro de software (*Software Supply Chain Attacks*) explotan vulnerabilidades presentes en estas dependencias.

* **Herramientas en Python:**
  * **`pip-audit`:** Desarrollada bajo los auspicios de la OpenSSF y PyPA. Audita el entorno de paquetes o archivos `requirements.txt` consultando la base de datos de vulnerabilidades abiertas de Google (**OSV - Open Source Vulnerabilities**).
  * **`Safety`:** Compara las dependencias instaladas contra la base de datos de vulnerabilidades de seguridad de PyUp.
  * **OWASP Dependency-Check:** Identifica CVEs públicas en librerías de múltiples lenguajes.

```bash
# Auditoría de dependencias mediante pip-audit generando salida JSON
pip-audit -r requirements.txt -f json -o sca_report.json
```

## 3. Escaneo de Infraestructura, Contenedores y Cumplimiento

Más allá del código de la aplicación, el pipeline debe verificar los entornos donde este se ejecuta:

### 3.1. Auditoría de Imágenes de Contenedores
Los contenedores Docker pueden heredar vulnerabilidades de sus imágenes base o incluir binarios con fallos conocidos.
* Mediante scripts de Python se invoca a herramientas de escaneo como **Trivy** o **Clair**.
* Python procesa el archivo JSON devuelto, extrayendo los identificadores CVE y los puntajes CVSS (*Common Vulnerability Scoring System*). Si se detecta un CVE con puntuación $CVSS \ge 9.0$ (Severidad Crítica), el contenedor no es subido al registro (*Container Registry*).

### 3.2. Infraestructura como Código (IaC) y Cumplimiento (*Compliance as Code*)
Los entornos en la nube se definen mediante plantillas de Terraform, CloudFormation o Kubernetes Manifests.
* Herramientas como **Checkov** o **tfsec** auditan que los recursos no expongan puertos inseguros (como el puerto 22 o 3389 abierto a `0.0.0.0/0`), que los buckets S3 tengan el cifrado en reposo habilitado y que las políticas IAM cumplan el principio de mínimo privilegio.
* Python valida que las plantillas cumplan las normativas de la organización (ISO 27001, SOC 2, PCI-DSS, NIST SP 800-53).

## 4. Gestión Automatizada de Secretos y Prevención de Fugas

Uno de los incidentes de seguridad más habituales en desarrollo es la inclusión accidental de claves de API, certificados privados, tokens de acceso personal y credenciales de bases de datos dentro del historial de Git.

```
┌───────────────────────────────────────────────────────────────────────────────────────────┐
│                           CICLO SEGURO DE GESTIÓN DE SECRETOS                             │
└─────────────────────────────────────────────┬─────────────────────────────────────────────┘
                                              │
 ┌──────────────────────────────────────┐     │     ┌──────────────────────────────────────┐
 │     ESCÁNER DE SECRETOS EN CI        │     │     │      GESTOR CENTRALIZADO (VAULT)     │
 │ Detecta regex de API Keys y Tokens   │     │     │ HashiCorp Vault / AWS Secrets Manager│
 └──────────────────┬───────────────────┘     │     └──────────────────┬───────────────────┘
                    │                         │                        │
                    ▼                         │                        ▼
       ¿Credencial en código fuente?          │            Inyección Dinámica en Memoria
           ├── SÍ ──► BLOQUEAR BUILD          │            (Librería hvac / boto3)
           └── NO ──► CONTINUAR PIPELINE      │            Variables efímeras sin persistir
```

### 4.1. Detección Preventiva
* Herramientas orquestadas por Python como `detect-secrets`, `truffleHog` o `gitleaks` escanean el código en busca de entropía elevada y cadenas coincidentes con patrones de proveedores conocidos (AWS Keys `AKIA...`, GitHub Tokens `ghp_...`).
* Python bloquea el commit a través de *pre-commit hooks* antes de que el código salga de la estación del desarrollador.

### 4.2. Inyección Dinámica en Tiempo de Ejecución con `hvac`
Los secretos nunca deben almacenarse en archivos de configuración ni en variables de entorno fijas del servidor CI. Deben ser solicitados bajo demanda a un almacén seguro como **HashiCorp Vault**:

```python
import hvac
import os

def retrieve_database_credentials() -> dict:
    """
    Obtiene credenciales efímeras desde HashiCorp Vault utilizando el token del runner de CI.
    """
    vault_client = hvac.Client(
        url=os.environ.get("VAULT_ADDR", "https://vault.internal.corp:8200"),
        token=os.environ.get("VAULT_TOKEN")
    )

    if not vault_client.is_authenticated():
        raise PermissionError("Fallo de autenticación con el servicio Vault corporativo.")

    secret_response = vault_client.secrets.kv.v2.read_secret_version(
        path="ci/database_credentials"
    )
    
    return secret_response['data']['data']
```

## 5. Política como Código (*Policy as Code*) y Compuertas de Calidad (*Security Quality Gates*)

Una **Compuerta de Seguridad (*Security Quality Gate*)** es una condición lógica estricta que determina si una compilación está autorizada para avanzar a la siguiente fase del pipeline o debe ser abortada inmediatamente.

```
                  ┌───────────────────────────────┐
                  │    EJECUCIÓN DE PRUEBAS       │
                  │    (Bandit, pip-audit, Trivy) │
                  └───────────────┬───────────────┘
                                  │
                                  ▼
                  ┌───────────────────────────────┐
                  │  SCRIPT PYTHON: SECURITY GATE │
                  │  (Evalúa umbrales de política)│
                  └───────────────┬───────────────┘
                                  │
                 ┌────────────────┴────────────────┐
                 │                                 │
           ¿Pasa Umbrales?                  ¿Falla Umbrales?
                 │                                 │
                 ▼                                 ▼
        ┌──────────────────┐             ┌──────────────────┐
        │ sys.exit(0)      │             │ sys.exit(1)      │
        │ CONTINUAR BUILD  │             │ DETENER PIPELINE │
        └──────────────────┘             └──────────────────┘
```

> [!IMPORTANT]
> **El Código de Salida del Sistema (`sys.exit()`):**
> En todos los sistemas operativos y motores de CI/CD (Linux, Windows, Jenkins, GitLab, GitHub Actions), un comando que termina con código `0` indica éxito. Cualquier código de retorno distinto de cero (generalmente `1`) indica un fallo fatal. Los scripts de Python utilizan `sys.exit(1)` para detener el pipeline e impedir que código inseguro llegue a producción.

## 6. Integración de Python con Sistemas CI/CD

Python se acopla a las canalizaciones a través de tres mecanismos principales:

### 6.1. Ejecución Directa en el Archivo de Configuración del Pipeline
Los motores de CI/CD declaran sus fases en archivos YAML o Groovy. Python puede ser invocado directamente en las instrucciones de ejecución:

#### Ejemplo en GitHub Actions (`.github/workflows/security.yml`):
```yaml
name: DevSecOps Security Pipeline

on: [push, pull_request]

jobs:
  security-audit:
    runs-on: ubuntu-latest
    steps:
      - name: Checkout del Repositorio
        uses: actions/checkout@v3

      - name: Configurar Entorno Python
        uses: actions/setup-python@v4
        with:
          python-version: '3.11'

      - name: Instalar Dependencias y Herramientas de Seguridad
        run: |
          python -m pip install --upgrade pip
          pip install bandit pip-audit -r requirements.txt

      - name: Ejecutar SAST (Bandit)
        run: bandit -r ./src -f json -o bandit_output.json || true

      - name: Ejecutar SCA (pip-audit)
        run: pip-audit -r requirements.txt -f json -o sca_output.json || true

      - name: Evaluar Security Quality Gate con Python
        run: python scripts/security_gate.py --bandit bandit_output.json --sca sca_output.json
```

### 6.2. Integración con APIs REST de Gestión de Incidentes
Cuando una compuerta de seguridad detecta vulnerabilidades críticas, un script en Python puede interactuar automáticamente con la API de **Jira** o **Slack** para notificar al equipo de seguridad y registrar un ticket con el informe forense:

```python
import json
import requests

def notify_security_channel(webhook_url: str, alert_message: str):
    """
    Envía una alerta estructurada al canal de respuesta a incidentes del SOC en Slack.
    """
    payload = {
        "text": f":rotating_light: *ALERTA DEVSECOPS - BUILD BLOQUEADA* :rotating_light:\n{alert_message}"
    }
    response = requests.post(webhook_url, json=payload, timeout=10)
    if response.status_code != 200:
        print(f"Error al enviar notificación a Slack: {response.status_code}")
```

## 7. Script Integral: Orquestador de Security Quality Gate en Python

A continuación se presenta un script corporativo completo (`security_gate.py`) diseñado para ser ejecutado en cualquier pipeline CI/CD. Este script procesa los reportes de **SAST (Bandit)** y **SCA (pip-audit)**, evalúa la política de seguridad y determina si la compilación debe aprobarse o rechazarse:

```python
"""
security_gate.py - Evaluador de Políticas DevSecOps para Pipelines CI/CD
Autor: Equipo de Ciberseguridad / SOC
Propósito: Evaluar hallazgos SAST y SCA, aplicar Policy-as-Code y controlar el build.
"""

import argparse
import json
import os
import sys
from typing import Any, Dict, List

# Definición de la Política Corporativa de Seguridad
# Límites máximos tolerados de vulnerabilidades antes de abortar el pipeline
MAX_ALLOWED_HIGH_SEVERITY_SAST = 0
MAX_ALLOWED_MEDIUM_SEVERITY_SAST = 2
BLOCK_ON_ANY_KNOWN_CVE_SCA = True

def parse_bandit_report(filepath: str) -> Dict[str, int]:
    """
    Parsea el archivo JSON generado por Bandit y clasifica los hallazgos por severidad.
    """
    if not os.path.exists(filepath):
        print(f"[!] Advertencia: No se encontró el reporte SAST en: {filepath}")
        return {"HIGH": 0, "MEDIUM": 0, "LOW": 0}

    with open(filepath, "r", encoding="utf-8") as f:
        data = json.load(f)

    metrics = {"HIGH": 0, "MEDIUM": 0, "LOW": 0}
    for result in data.get("results", []):
        severity = result.get("issue_severity", "LOW").upper()
        if severity in metrics:
            metrics[severity] += 1

    return metrics

def parse_pip_audit_report(filepath: str) -> List[Dict[str, Any]]:
    """
    Parsea el archivo JSON generado por pip-audit y recopila las vulnerabilidades CVE detectadas.
    """
    if not os.path.exists(filepath):
        print(f"[!] Advertencia: No se encontró el reporte SCA en: {filepath}")
        return []

    with open(filepath, "r", encoding="utf-8") as f:
        data = json.load(f)

    vulnerabilities = []
    # pip-audit estructura los datos en formato de lista de dependencias
    dependencies = data.get("dependencies", []) if isinstance(data, dict) else data
    for dep in dependencies:
        for vuln in dep.get("vulns", []):
            vulnerabilities.append({
                "package": dep.get("name"),
                "version": dep.get("version"),
                "cve_id": vuln.get("id"),
                "fix_versions": vuln.get("fix_versions")
            })

    return vulnerabilities

def main():
    parser = argparse.ArgumentParser(description="Evaluador de Seguridad DevSecOps para CI/CD")
    parser.add_argument("--bandit", required=True, help="Ruta al archivo JSON de Bandit (SAST)")
    parser.add_argument("--sca", required=True, help="Ruta al archivo JSON de pip-audit (SCA)")
    args = parser.parse_args()

    print("=======================================================")
    print("      EVALUACIÓN DE COMPUERTA DE SEGURIDAD (DEVSECOPS)  ")
    print("=======================================================")

    # 1. Evaluación de SAST
    sast_metrics = parse_bandit_report(args.bandit)
    print(f"\n[+] Resultados SAST (Bandit):")
    print(f"    - Severidad Alta (HIGH)  : {sast_metrics['HIGH']}")
    print(f"    - Severidad Media (MEDIUM): {sast_metrics['MEDIUM']}")
    print(f"    - Severidad Baja (LOW)   : {sast_metrics['LOW']}")

    # 2. Evaluación de SCA
    sca_findings = parse_pip_audit_report(args.sca)
    print(f"\n[+] Resultados SCA (pip-audit):")
    print(f"    - Dependencias vulnerables encontradas: {len(sca_findings)}")
    for finding in sca_findings:
        print(f"      * Paquete: {finding['package']} (v{finding['version']}) -> {finding['cve_id']}")

    # 3. Aplicación de la Política de Calidad (Quality Gate)
    policy_violation = False
    reasons = []

    if sast_metrics["HIGH"] > MAX_ALLOWED_HIGH_SEVERITY_SAST:
        policy_violation = True
        reasons.append(f"Se encontraron {sast_metrics['HIGH']} vulnerabilidades SAST de severidad ALTA (Límite: {MAX_ALLOWED_HIGH_SEVERITY_SAST}).")

    if sast_metrics["MEDIUM"] > MAX_ALLOWED_MEDIUM_SEVERITY_SAST:
        policy_violation = True
        reasons.append(f"Se encontraron {sast_metrics['MEDIUM']} vulnerabilidades SAST de severidad MEDIA (Límite: {MAX_ALLOWED_MEDIUM_SEVERITY_SAST}).")

    if BLOCK_ON_ANY_KNOWN_CVE_SCA and len(sca_findings) > 0:
        policy_violation = True
        reasons.append(f"Se encontraron {len(sca_findings)} dependencias de terceros con CVEs conocidas activas.")

    print("\n-------------------------------------------------------")
    if policy_violation:
        print("[X] DECISIÓN: PIPELINE ABORTADO POR POLÍTICA DE SEGURIDAD")
        print("    Causas del bloqueo:")
        for reason in reasons:
            print(f"    - {reason}")
        print("-------------------------------------------------------")
        sys.exit(1)  # Retorno no-cero: detiene el pipeline en el runner CI/CD
    else:
        print("[V] DECISIÓN: COMPILACIÓN APROBADA - CUMPLE CON LAS POLÍTICAS")
        print("-------------------------------------------------------")
        sys.exit(0)  # Retorno cero: permite que el build continúe hacia producción

if __name__ == "__main__":
    main()
```

## 8. Resumen y Puntos Clave

1. **DevSecOps y Shift-Left:** Integración sistemática de controles de seguridad en cada fase del pipeline CI/CD, reduciendo los costes de mitigación hasta 30-100 veces en comparación con la detección tardía en producción.
2. **SAST con Python (`Bandit`):** Inspección estática del código fuente y el árbol de sintaxis abstracta (AST) para prevenir inyecciones, llamadas inseguras y exposición de secretos antes de compilar.
3. **DAST con Python (OWASP ZAP):** Simulación dinámica de ataques de caja negra contra la aplicación en ejecución en entornos de staging.
4. **SCA con Python (`pip-audit` / `Safety`):** Auditoría obligatoria de dependencias de terceros para blindar la cadena de suministro de software contra vulnerabilidades públicas (CVEs).
5. **Gestión de Secretos:** Prohibición absoluta de credenciales en repositorios; uso de librerías como `hvac` para consultar almacenes seguros (HashiCorp Vault) e inyectar secretos efímeros en memoria durante el build.
6. **Política como Código y Quality Gates:** Uso de scripts en Python que evalúan los reportes JSON de seguridad y emiten `sys.exit(1)` para abortar automáticamente cualquier compilación que vulnere los umbrales corporativos.
