# Sintaxis, Legibilidad y Estándares PEP 8 en Python para Ciberseguridad

En esta undécima entrega del **Curso 7: Automatizar tareas de ciberseguridad con Python**, se analizan en detalle las directrices de la guía oficial de estilo **PEP 8 (*Python Enhancement Proposal 8*)**, la documentación técnica mediante **comentarios de una sola línea, bloques multilínea y cadenas de documentación (*docstrings*, PEP 257)**, las reglas estrictas de **indentación en estructuras anidadas**, y la prevención de los **errores de sintaxis (*SyntaxError*)** más frecuentes en el desarrollo de herramientas del Centro de Operaciones de Seguridad (SOC).

## 1. La Legibilidad como Requisito de Seguridad

En el desarrollo de software tradicional, el código ilegible genera deuda técnica; en **ciberseguridad**, el código ilegible genera **brechas de seguridad y fallos en la respuesta a incidentes**. Cuando un analista debe modificar un script de aislamiento de red bajo la presión de un ataque de ransomware activo, la claridad sintáctica y la documentación explícita marcan la diferencia entre contener la amenaza o provocar una caída no deseada en los servidores corporativos.

## 2. Documentación Efectiva: Comentarios y Docstrings

Los **comentarios** son notas destinadas a los seres humanos que el intérprete de Python ignora por completo durante la ejecución.

### 2.1. Comentarios de una Sola Línea (`#`)
* Comienzan con el carácter numeral (`#`), seguido de un espacio en blanco.
* **Límite de Longitud PEP 8:** No deben superar los **72 a 79 caracteres** por línea para evitar el desplazamiento horizontal (*scrolling*) en terminales y editores divididos.
* **Buenas Prácticas:** No explique lo obvio (el *qué*); explique la intención y el contexto de seguridad (el *por qué*).

```python
# ❌ INCORRECTO: Comentario redundante que no aporta valor
count = count + 1 # Suma 1 a la variable count

# ✔️ CORRECTO: Explica el contexto de la regla de detección
# Incrementa el contador de fallos para evaluar posible ataque de diccionario
count = count + 1

# Imprime los nombres de los activos para auditoría de inventario
computer_assets = ["laptop1", "desktop20", "smartphone03"]
for asset in computer_assets:
    print(asset)
```

---

### 2.2. Comentarios Multilínea con Bloques de Numerales (`#`)
Cuando la explicación técnica requiere más de una línea, se utilizan caracteres `#` consecutivos, manteniendo todas las líneas alineadas y por debajo de 79 caracteres:

```python
# La función remaining_login_attempts() recibe dos parámetros enteros:
# el límite máximo de intentos permitidos y el total de intentos realizados.
# Devuelve un entero que representa los intentos restantes antes del bloqueo.
def remaining_login_attempts(maximum_attempts, total_attempts):
    return maximum_attempts - total_attempts
```

---

### 2.3. Cadenas de Documentación (*Docstrings*, PEP 257)
A diferencia de los comentarios regulares con `#`, una **docstring** es una cadena literal delimitada por **comillas triples (`""" """`)** situada inmediatamente debajo de una función, clase o módulo:

```python
def remaining_login_attempts(maximum_attempts, total_attempts):
    """Calcula y devuelve el margen de reintentos antes del bloqueo.

    Parámetros:
        maximum_attempts (int): Umbral global de intentos permitidos.
        total_attempts (int): Intentos registrados en el evento.

    Retorna:
        int: Diferencia matemática que representa los intentos restantes.
    """
    return maximum_attempts - total_attempts
```

#### Ventaja Computacional de las Docstrings:
Las docstrings no son descartadas por el compilador; se almacenan en el atributo especial `__doc__` del objeto y quedan disponibles para herramientas automáticas de documentación e inspección interactiva en consola:

```python
# Inspección en tiempo de ejecución durante un incidente
print(remaining_login_attempts.__doc__)
help(remaining_login_attempts)
```

## 3. Indentación y Jerarquía en Estructuras Anidadas

En Python, la **indentación** (sangría) no es un adorno estético; es el mecanismo formal del lenguaje para definir el alcance (*scope*) y la jerarquía de los bloques de código.

### 3.1. Reglas Estrictas de Indentación
* **4 Espacios por Nivel:** La guía PEP 8 prohíbe el uso de tabuladores puros (`\t`) y exige el uso consistente de **cuatro espacios en blanco** por cada nivel de anidamiento.
* **Prohibición de Mezclas:** Mezclar tabuladores y espacios en el mismo script arroja un error fatal `TabError: inconsistent use of tabs and spaces in indentation`.

### 3.2. Anidamiento Progresivo (Cálculo de Espacios)
Cada estructura subordinada incrementa la sangría en 4 espacios adicionales:

```python
count = 0
login_status = True

# Nivel 0 (Raíz del script): 0 espacios
while login_status == True:
    # Nivel 1 (Cuerpo del bucle while): 4 espacios
    print("Try again.")
    count = count + 1
    
    if count == 4:
        # Nivel 2 (Cuerpo de la sentencia condicional if): 8 espacios
        login_status = False

# Nivel 0 (Fuera del bucle): 0 espacios
print("Proceso de autenticación finalizado.")
```

```
JERARQUÍA VISUAL DE ESPACIOS:
[0 espacios] while login_status == True:
[4 espacios] ├── print("Try again.")
[4 espacios] ├── count = count + 1
[4 espacios] └── if count == 4:
[8 espacios]     └── login_status = False
```

## 4. Los Errores de Sintaxis más Frecuentes en Scripts del SOC

Un `SyntaxError` se produce cuando el código viola la gramática formal de Python, impidiendo que el intérprete pueda compilar el script a bytecode.

```
┌───────────────────────────────────────────────────────────────────────────────────────────┐
│                     ERRORES DE SINTAXIS Y TIPADO MÁS COMUNES EN EL SOC                    │
├──────────────────────────┬─────────────────────────────┬──────────────────────────────────┤
│ Tipo de Fallo            │ Código Incorrecto           │ Código Corregido (PEP 8)         │
├──────────────────────────┼─────────────────────────────┼──────────────────────────────────┤
│ **Omisión de Dos Puntos**│ `if status == 200`          │ `if status == 200:`              │
│                          │ `def check_alert()`         │ `def check_alert():`             │
│                          │ `for ip in ip_list`         │ `for ip in ip_list:`             │
├──────────────────────────┼─────────────────────────────┼──────────────────────────────────┤
│ **Comillas en Números**  │ `port = "443"`              │ `port = 443`                     │
│                          │ *(Impide cálculos directos)*│ *(Tipo entero correcto)*         │
├──────────────────────────┼─────────────────────────────┼──────────────────────────────────┤
│ **Comillas en Booleanos**│ `is_admin = "False"`        │ `is_admin = False`               │
│                          │ *(¡"False" evalúa a True!)* │ *(Booleano lógico real)*         │
├──────────────────────────┼─────────────────────────────┼──────────────────────────────────┤
│ **Delimitadores Listas** │ `users = ("admin", "user")` │ `users = ["admin", "user"]`      │
│                          │ *(Paréntesis crea tupla)*   │ *(Corchetes crean lista mutable)*│
└──────────────────────────┴─────────────────────────────┴──────────────────────────────────┘
```

### 4.1. El Peligro Crítico del Booleano Entrecomillado (`"False"`)

Este es uno de los errores lógicos más catastróficos en ciberseguridad. En Python, **cualquier cadena de texto no vacía evalúa implícitamente a `True`** en una condición:

```python
# FALLO CRÍTICO DE SEGURIDAD
usuario_bloqueado = "False" # Se asignó como cadena con comillas en lugar de booleano

if usuario_bloqueado:
    # Como bool("False") es True, ¡este bloque se ejecuta indebidamente!
    print("[ERROR DE AUTORIZACIÓN] La cuenta ha sido bloqueada por equivocación.")
```

#### Corrección:
```python
usuario_bloqueado = False # Sin comillas: booleano puro
if usuario_bloqueado:
    print("Cuenta bloqueada.")
else:
    print("Acceso permitido.") # Flujo correcto
```

---

### 4.2. Comparación Léxica vs. Numérica por Comillas Indebidas
Si se almacenan puertos o contadores como cadenas entrecomilladas, los operadores relacionales aplican orden alfabético Unicode, no matemático:

```python
# Error: "80" > "443" evalúa a True porque el carácter '8' es mayor que '4'
puerto_a = "80"
puerto_b = "443"
print(puerto_a > puerto_b) # Devuelve True (¡Error de lógica matemática!)

# Corrección mediante enteros
puerto_a = 80
puerto_b = 443
print(puerto_a > puerto_b) # Devuelve False (Correcto)
```

## 6. Matriz Resumen de Reglas de Sintaxis y Estilo PEP 8

| Elemento | Regla de la Guía PEP 8 | Ejemplo Válido | Ejemplo No Válido |
| :--- | :--- | :--- | :--- |
| **Indentación** | Exactamente 4 espacios por nivel. | `    print("OK")` | `  print("OK")` (2 esp.) o `\t` |
| **Longitud de Línea** | Máximo 79 caracteres para código. | Dividir cadenas largas en varias líneas | Líneas de 150 caracteres |
| **Variables y Func.** | `snake_case` (minúsculas y guiones bajos).| `failed_login_count` | `FailedLoginCount` o `failedLogins` |
| **Constantes** | `SCREAMING_SNAKE_CASE`. | `MAX_THRESHOLD = 5` | `max_threshold = 5` |
| **Espaciado Operador**| 1 espacio antes y después de operadores. | `a = b + 1` | `a=b+1` |
| **Dos Puntos** | Sin espacio antes, salto indentado después. | `if condition:` | `if condition :` |

## 7. Casos Prácticos en Operaciones de Ciberseguridad (SOC)

### Caso 1: Refactorización de un Script de Auditoría de Cuentas Conforme a PEP 8

#### Código Crudo Original (Deficiente y propenso a errores):
```python
def check(u,a):
if a>5:print("Alert:"+u)
else:print("OK")
```

#### Código Refactorizado Profesional (PEP 8 y PEP 257):
```python
def evaluate_user_risk(username, failed_attempts):
    """Evalúa el nivel de riesgo de un usuario según sus intentos fallidos.

    Parámetros:
        username (str): Identificador de la cuenta corporativa.
        failed_attempts (int): Número de accesos denegados registrados.
    """
    threshold = 5
    
    if failed_attempts > threshold:
        print(f"[ALERTA SOC] Usuario {username} superó el umbral de intentos ({failed_attempts}).")
    else:
        print(f"[CONFORME] Acceso estándar para el usuario: {username}")

# Invocación limpia
evaluate_user_risk("bmoreno", 7)
```

## 8. Puntos Clave para el Analista de Ciberseguridad

* **La Legibilidad es Seguridad:** Un código estructurado bajo PEP 8 previene errores lógicos en scripts críticos de respuesta y permite auditorías rápidas por parte de otros miembros del SOC.
* **Comentarios Oportunos:** Usar `#` para explicar la intención y contexto de negocio, manteniendo las líneas por debajo del umbral de 79 caracteres.
* **Docstrings Estandarizadas (PEP 257):** Utilizar comillas triples `""" """` en funciones para describir parámetros y retornos, accesibles mediante `help()`.
* **Indentación Obligatoria:** 4 espacios por nivel jerárquico; nunca usar tabuladores para evitar colapsos por `TabError`.
* **Sintaxis Rigurosa:** Terminar siempre encabezados con dos puntos `:`, no entrecomillar valores booleanos ni numéricos para evitar comportamientos anómalos en condiciones lógicas y comparaciones.
